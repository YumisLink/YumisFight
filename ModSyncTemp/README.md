# Yumis ModSync

独立 Windows 模组同步器。玩家操作见 [使用说明](../playerread/启动器与模组同步.md)。它不修改 PCL，也不修改游戏 Java 代码。

## 开发与构建

使用 .NET SDK 10，构建入口 `./ModSyncTemp/build.ps1`。输出、obj、资源副本、日志和验证资料均位于仓库 `temp/mod-sync`。用户提供的 PCL 源码 ZIP 只作研究参考，解压副本位于 temp，不进入工具源码。

首次部署运行 `./ModSyncTemp/setup-server.ps1`。它使用本机 OpenSSH 的 `homo`，在既有宝塔 nginx 上增加独立 HTTPS vhost，生成专用服务器证书与随机只读下载口令。私有构建配置写入 `temp/mod-sync/private/profile.json`，不打印口令。保留此配置供后续重新构建；不得提交或单独上传。

`build.ps1` 原样内嵌本机已核实的官方 PCL 2.13.1.1，并检查 SHA-256。不会提取或复制它的内部应用凭据。玩家 EXE 包含 .NET 运行时和官方 PCL 原样副本，管理员 SSH 私钥仍由 Windows OpenSSH 管理。

## 管理员发布

双击同一 EXE 的管理员快捷入口，或运行 `YumisModSync.exe --publish`。选取正确隔离实例的 mods，点击“发布更新”。自动排除非 .jar 文件；按本机字节识别来源，有外部链接的文件只发布元数据，其余文件才上传。PCL 缓存未知版本或无法精确匹配时标记未知，不使用 `UpdateFile`。

新加模组需要补 CF 来源时，可先在原版 PCL 的该版本 Mod 管理页按 F5，让 PCL 更新自身来源缓存。发布器随后读取当前版本记录；没有可靠链接时仍能将文件托管到服务器。

已发布清单中的外部来源会按完整SHA-256和大小复用于后续发布，因此Windows清理PCL临时缓存不会遗失已核实的来源。

自动化管理员入口：`--publish --headless --source <mods绝对路径> --output <本机temp目录> --report <本机temp中的JSON路径>`。首次部署和 SSH 身份需事先配置；玩家无法仅凭只读下载口令发布内容。

发布器先生成清单、校验源文件、上传到 incoming，然后通过正式的 SSH 发布脚本验证所有服务器对象，再原子切换 `current.json`。历史清单与内容对象保留，不自动删除历史版本。HTTP 仅开放当前清单和内容对象，secure/incoming/releases 不作为下载目录开放。

## 协作与安全边界

下载助手的公开整合包导入会准备一个临时 Minecraft 原版实例。只列仍缺失的 CF JAR，使用唯一实例名；不安装 NeoForge，不启动该实例。助手可复制已登记游戏目录中的资源，缺失部分仍需下载。

成功需同时满足本次日志成功状态、mrpack 已被清理、每个 JAR 大小和 SHA-256 匹配。只读取文件出现或进程退出不算成功。助手独立目录内的缓存可复用；仅撤销本工具新增的目录登记，不回滚 PCL 账号、登录 token 等正常缓存。

服务器证书使用公钥固定验证；密码随程序分发，只代表“拿到程序即可下载”，不提供个人身份区分。口令或公钥改变需重新分发 EXE。外部源没有服务器镜像时，失败会停止本次更新。

协议与恢复设计见 [开发说明](../doc/Mods同步器开发说明.md)。仅工具验证已获本会话授权；游戏测试继续暂停。不得将 temp、截图、验证脚本或报告混入上传包。
